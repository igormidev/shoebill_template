# Initial context
In a short: I want to build a saas where the users will be able to talk with a AI in a chat-bot like style in order to generate PDF's template and receive a REST endpoint that they can then call to generate PDF on top of the template created. So, with a given payload, based on the template they previously builted with AI in the chat interation, the will receive the pdf.

Why I want to create this?
Some companies need generate to generate PDF for there clients (this is the pain). Most of them have a template that they manually edit or that is automated to receive a payload of data (that represents the dynamic data that will change between one pdf and other) and with that they generate the pdf. But there is no real good solution here because creating that pdf is a pain in the ass and mantaining it as well. More then that: The core-business of those companies is not handling the infra to generate pdf's (that is a costly things in terms of computing power), so most of them try solutions like [pdfforge](https://apitemplate.io/) or [pdfgeneratorapi](https://pdfgeneratorapi.com/) and much other's that exist but all of them are based in you mannualy inputing the pdf html/css and this might be tuff for non tecnical people. And the pdf generated are quite bad loking in terms of ui.

# Key differentiators
The main differentiators between the saas that I want you to build and the ones that already exists are, mainly, two:
- Low friction to have a working template.
- Easy to understand UI for less-tecnical people.
- The possibility to actually see the template/product before paying anything.
- The possibility of auto-translating the pdf to multiple languages.

## Low friction (login-less test)
We wan't the user to need to input the less things as possible. In fact, the only thing really required is the a example of a JSON payload the user would use.
This saas is all about giving a REST endpoint where the user will be able to send a payload with dynamic values and receive a url that points to the generated pdf in the response.
 
AI will create the template. But it needs somethings, like:
- A prompt. A text explanation about what the user expects from the template (how many pages, the desired structure, if he wants a header or footer, ui-style etc...)
- A input sample. The AI needs to have a example of a json input so it can correctly create the dynamic fields in the template.
- A schema. So the endpoint can correctly show a error message of what is missing for the user if he does not send a data in his requests. This also helps AI to know what data are nullable. I will talk more about there throught the prompt.
- A title/description so the user can identify this template later in the dashboard of the site

He wan't this to be the most friction-less as possible. So, we will only ask for the JSON input sample. And then, we will use AI to infer, based on the JSON sample, and create the schema and the prompt that describes how the PDF should be.

You will make a AI call and you will create a awesome prompt with great prompt engeniring that explains what the app is and what we are trying to achieve, that is to deduce, by the sample json, that the user is trying to do and create a prompt describing how the page should be and also the schema that is appropriate to it and also a title/description for the pdf template.

All of this will be editable for the user. The user can totally erase the prompt generated by ai and put his own if he whats, the same thing for the scheme that he can add/remove or edit atribute types and names – this will be a default so the user that is lazy can continue to thoose things generated for him or do any quick/deep change if he think is wanted.

In the prompt that the AI will create based on the json, ask AI to tell about how many pages will exist, if it is apropriado to put footer/header, what will exist in each page – what data will apear where, the style of things.

Never make translation related logic in the logic layer. Also don't make "display dialog/buttonsheets" logics in the logic layer as well.
Allways prefer to use riverpod to listen the state change in the screen that the listening is relevan t and, if it listen to a state that has error it will then do the display of the error.


For all AI processes that will have a thinking time, we should return a stream of the thought process. I want to do this so that the user doesn't just see a "loading" message without knowing if something is happening or if a error occoured.
I even already created a file that you should check, the [ai_thinking_chunk.spy.yaml](sirius_server/lib/src/entities/others/ai_thinking_chunk.spy.yaml) . You will return allways a model that will have it and the final response for the user. For instance: In the ui of "## New PDF template form ( Dialog )" you will make a request to AI that will return a schemed response. Even with a schema response, you will can stream the thinking proccess – and you should do it.
So, you will create a model like:
```
class: [Name]ResultChunk
fields:
    finalResultChunk: TargetModel?
    thinkingChunk: AiThinkingChunk?
```
Always the same pattern, a model with 2 variables, one beeing the `finalResultChunk` and the other the `thinkingChunk`.
For each thinking chunk in the ui you will display it. You should not show only the newest chunk, you should instead concatenate one on other until the moment there is X number of words (words are separated by spaces).
This "X" will depend on the UI because some UI have more spaces and other have less. 
Use something like:
```dart
extension TakeLastExtension<T> on List<T> {
  List<T> takeLast(int count) {
    if (count <= 0) {
      return [];
    }

    if (count >= length) {
      return List<T>.from(this);
    }

    return sublist(length - count);
  }

  String recentValues(int count) {
    return takeLast(count).join('');
  }
}
```
